# Linux Log Hunter

Инструмент на Python для поиска атак и сбоев в Linux-логах. Читает `auth.log` (sshd) и nginx `access.log`,
находит подбор паролей, сканирование, атаки на веб-приложение и всплески ошибок 5xx, ставит важность и технику
MITRE ATT&CK, при необходимости отправляет итог в Telegram.

Только стандартная библиотека Python 3.10+, без внешних зависимостей.

## Что находит

| Детект | Правило (по умолчанию) | Важность | MITRE ATT&CK |
|---|---|---|---|
| `ssh_bruteforce` | 5 неудачных входов с одного IP за 60 с | HIGH | T1110.001 |
| `ssh_compromise` | успешный вход с IP не позже чем через 10 мин после подбора | CRITICAL | T1078 |
| `ssh_user_enum` | 5 разных несуществующих имён с одного IP за 60 с | MEDIUM | T1110 |
| `web_scan` | 20 ответов 4xx одному клиенту за 60 с | MEDIUM | T1595.002 |
| `web_attack` | в запросе есть сигнатура (`../`, `/etc/passwd`, `union select`, `<script`, `/.env`, `/.git/`, `cmd.exe`, `${jndi:` и др.) | HIGH | T1190 |
| `availability_spike` | 100 и больше ответов 5xx за одну минуту | HIGH | нет (инцидент доступности) |

Пороги лежат в `loghunter/config.py`. Для SSH и сканирования окна скользящие, а не по календарным минутам, поэтому
всплеск на стыке минут не теряется. Всплеск 5xx считается по календарным минутам. Один всплеск даёт один алерт со счётчиком событий.

## Быстрый старт

```bash
python -m loghunter --auth /var/log/auth.log --nginx /var/log/nginx/access.log --year 2026 --json alerts.json
```

Пример вывода:

```
[CRITICAL] ssh_compromise (T1078) 193.29.7.190 с 2026-11-04 08:13:18 UTC, событий: 1
[HIGH] ssh_bruteforce (T1110.001) 185.59.151.57 с 2026-11-01 02:10:41 UTC, событий: 12
[HIGH] web_attack (T1190) 45.231.131.115 с 2026-11-01 16:17:33 UTC, событий: 3
[HIGH] availability_spike (-) минута 2026-11-05 09:08:00 UTC с 2026-11-05 09:08:00 UTC, событий: 150
```

Код возврата 1, если найдены алерты, и 0, если нет (удобно для cron и скриптов).

Уведомление в Telegram:

```bash
export TG_TOKEN=... TG_CHAT_ID=...
python -m loghunter --auth /var/log/auth.log --telegram
```

Запуск по расписанию, например каждые 5 минут:

```
*/5 * * * * cd /opt/linux-log-hunter && python -m loghunter --auth /var/log/auth.log --nginx /var/log/nginx/access.log --year 2026 --telegram
```

Docker:

```bash
docker build -t loghunter .
docker run --rm -v /var/log:/logs:ro loghunter --auth /logs/auth.log --nginx /logs/nginx/access.log --year 2026
```

## Результаты замеров

Замеры на синтетических логах: фоновый трафик плюс заранее заложенные атаки (ссылка на эталон: `truth.json`).
Обе версии работают с одними и теми же порогами и должны найти одно и то же.

- **v1 (`naive/`)**: первая версия, написанная «в лоб».
- **v2 (`loghunter/`)**: после профилирования v1.

Измерялось отдельным процессом на каждый запуск, значение времени это медиана из трёх запусков, память это пик RSS.
Время включает разбор и анализ обоих файлов.

| Размер (строк в двух файлах / МБ) | v1 | v2 | Ускорение | Память v1 → v2 |
|---|---|---|---|---|
| 200 тыс. / 25 МБ | 1,11 с | 0,16 с | в 6,9 раза | 75 → 21 МБ |
| 2 млн / 249 МБ | 11,27 с | 1,56 с | в 7,2 раза | 587 → 22 МБ (в 26,7 раза меньше) |
| 10 млн / 1,25 ГБ | не запускалась | 7,92 с | | 23 МБ |

Пропускная способность v2: около 1,26 млн строк в секунду (около 157 МБ/с), v1: около 0,18 млн строк в секунду (около 22 МБ/с).
Память v2 не зависит от размера файла: 21 МБ на 200 тыс. строк и 23 МБ на 10 млн строк.

Качество на тех же данных (сверка с эталоном):

| Размер | Эталонных алертов | Найдено | Ложных срабатываний |
|---|---|---|---|
| 200 тыс. строк | 28 | 28 | 0 |
| 2 млн строк | 265 | 265 | 0 |
| 10 млн строк | 1325 | 1325 | 0 |

В данных есть «ловушки», которые не должны давать алерт: 4 неудачных входа за минуту (порог 5) и 15 ответов 4xx за 30 с (порог 20).

### Что именно ускорило

По профилю (`cProfile`) около 53% времени v1 уходило на `datetime.strptime`, ещё около 13% на `re.search` с неразобранными шаблонами.
Исправлено так:

1. Время считается без `datetime`: эпоха минуты кэшируется (не больше нескольких тысяч записей за неделю логов), секунды берутся срезом строки.
2. Строки без `sshd[` отбрасываются проверкой подстроки до запуска регулярок, шаблоны скомпилированы один раз.
3. Файл читается потоком, а не `readlines()`: память не растёт вместе с файлом.
4. Окна считаются очередью `deque`: добавить справа, убрать устаревшее слева, O(1) на событие. В v1 окно считалось перебором событий одного IP.
5. Раз в ~260 тыс. строк удаляются устаревшие окна, поэтому память остаётся ограниченной и при множестве разных IP.

## Воспроизвести замеры

```bash
python tools/gen_logs.py --lines 1000000 --out data/1000000   # генератор логов с эталоном
python tools/benchmark.py --sizes 100000 1000000 --repeat 3  # сравнение v1 и v2 + проверка по эталону
python tools/benchmark.py --sizes 5000000 --skip-naive       # 10 млн строк, только v2
python -m unittest discover -s tests -t .                    # 25 тестов
```

Результаты последнего запуска лежат в `benchmark_results.json` и `benchmark_results_10m.json`.
Абсолютное время зависит от компьютера (замеры сделаны на 2 ядрах, Python 3.13), отношение v1 к v2 должно быть близким.

## Структура

```
loghunter/        быстрая версия (v2)
  auth.py         sshd: подбор, вход после подбора, перебор имён
  web.py          nginx: сканирование, сигнатуры, всплеск 5xx
  report.py       текст, JSON, Telegram
  config.py       пороги, сигнатуры, MITRE
  __main__.py     командная строка
naive/            первая версия (v1), точка отсчёта для замеров
tools/            генератор логов и бенчмарк
tests/            unittest: пороги, окна, устойчивость к мусору, совпадение v1 и v2 с эталоном
```

## Ограничения

- Замеры и точность проверены на синтетических логах, а не на реальном трафике. Реальные логи шумнее, и пороги придётся подбирать под свой сервис.
- Один запуск читает файл целиком с начала, состояния между запусками нет (нет «хвоста» файла и учёта уже отправленных алертов). Для постоянного мониторинга нужно добавить запоминание позиции.
- В `auth.log` нет года, поэтому он передаётся параметром `--year`; смену года внутри одного файла программа не обрабатывает.
- Время в nginx читается без учёта часового пояса (смещение отбрасывается), для окон в секундах это допустимо, но абсолютное время в отчёте может отличаться на смещение.
- Обрабатываются только сообщения sshd и формат nginx combined; ротированные `.gz`-файлы нужно распаковать заранее.
